O Problema

1.Race condition em GPUs

Quando vários jobs usam a mesma GPU ao mesmo tempo, competem por memória e capacidade de processamento — com resultados imprevisíveis:

# Sem controle — 4 jobs simultâneos [08:00:00] Job-A inicia — aloca 6 GB VRAM [08:00:01] Job-B inicia — aloca 6 GB VRAM [08:00:02] Job-A: CUDA OOM — apenas 2 GB livres! [08:00:02] Job-B: CUDA OOM — crash silencioso [08:00:03] Job-C: resultados corrompidos (VRAM fragmentada) # Com o lock: [08:00:10] Jobs executam 1 por vez, sem conflito ✅

❌ Sem controle

Jobs competem por VRAM → OOM crash, resultados corrompidos.

✅ Com lock

Exclusão mútua → 1 job por vez, fila automática.

🚀 Com prioridade

Jobs urgentes passam à frente → máxima eficiência da equipe.

Teoria · Exclusão Mútua

2.flock — 1 job por vez

flock cria um lock de arquivo. Enquanto um processo o mantém, os demais bloqueiam até o primeiro terminar.

FlagSignificadoUso típico
-xLock exclusivo (padrão)Acesso exclusivo à GPU
-sLock compartilhadoLeitura simultânea de métricas
-nNon-blocking (falha rápido)Verificar se a GPU está livre
-w NTimeout em N segundosDesistir se demorar muito
-uLiberar lock manualmenteCleanup em trap de sinal
bash 
#!/usr/bin/env bash
# flock_gpu.sh — exclusão mútua para acesso à GPU
set -euo pipefail

LOCK_FILE="/var/lock/gpu_exclusive.lock"
PYTHON_SCRIPT="${1:-train.py}"
shift || true

echo "[$(date '+%H:%M:%S')] PID $$ aguardando lock..."

# -x: lock exclusivo  |  -w 0: espera indefinidamente
(
  flock -x 200
  echo "PID $$ adquiriu GPU — iniciando $PYTHON_SCRIPT"
  python3 "$PYTHON_SCRIPT" "$@"
  EXIT_CODE=$?
  echo "PID $$ liberou GPU (exit=$EXIT_CODE)"
  exit $EXIT_CODE
) 200>"$LOCK_FILE"
💡 No Git Bash do Windows não existe flock: usamos um lock por diretório (criar pasta é uma operação atômica — mesmo princípio). Em Linux/WSL, o flock real é usado automaticamente.

3.Sistema de fila com prioridade

Combinando lock + ordenação de arquivos, criamos uma fila com 3 níveis. Prioridade 1 executa antes de 3; empate desempata por tempo (FIFO).

bash 
#!/usr/bin/env bash
# gpu_queue.sh — fila de jobs com prioridade e logging
# Uso: ./gpu_queue.sh <prioridade> <nome_job> <script.py> [args...]
# Prioridades: 1=alta, 2=media, 3=baixa (FIFO dentro da mesma prioridade)
set -euo pipefail

PRIORIDADE="${1:-2}"; NOME_JOB="${2:-job_$$}"
SCRIPT="${3:-train.py}"; shift 3 2>/dev/null || true

QUEUE_DIR="/var/spool/gpu_queue"
LOCK_FILE="/var/lock/gpu_queue.lock"
LOG_FILE="/var/log/gpu_queue.log"
mkdir -p "$QUEUE_DIR"

# Ticket: prioridade + timestamp + nome => o sort ordena por prioridade
TICKET="${PRIORIDADE}_$(date +%Y%m%d_%H%M%S_%N)_${NOME_JOB}"
echo "$SCRIPT $*" > "$QUEUE_DIR/$TICKET"
echo "Job '$NOME_JOB' (prio=$PRIORIDADE) enfileirado: $TICKET" | tee -a "$LOG_FILE"

# Aguarda a vez (é o primeiro da fila?)
while true; do
    PROXIMO=$(ls "$QUEUE_DIR" 2>/dev/null | sort | head -1)
    [ "$PROXIMO" = "$TICKET" ] && break
    echo "Aguardando: $PROXIMO está à frente..."
    sleep 5
done

# Executa com lock exclusivo e sai da fila no fim
(
  flock -x 200
  START=$(date +%s)
  python3 "$SCRIPT" "$@"; EXIT_CODE=$?
  END=$(date +%s)
  echo "'$NOME_JOB' concluido em $((END-START))s (exit=$EXIT_CODE)" | tee -a "$LOG_FILE"
  rm -f "$QUEUE_DIR/$TICKET"
  exit $EXIT_CODE
) 200>"$LOCK_FILE"

Por que funciona? O nome do ticket começa pela prioridade; a ordenação lexicográfica coloca 1_… antes de 2_… antes de 3_…. O timestamp garante FIFO e unicidade.

4.Job de teste e lançamento em lote

python 
# train_job.py — job de treino simulado
import argparse, time, random, os
try:
    import torch
except Exception:
    torch = None

parser = argparse.ArgumentParser()
parser.add_argument("--nome", default="Job")
parser.add_argument("--epocas", type=int, default=3)
args = parser.parse_args()

print(f"[{args.nome}] PID={os.getpid()} | Épocas={args.epocas}")
device = "cuda" if (torch and torch.cuda.is_available()) else "cpu"
for epoca in range(1, args.epocas + 1):
    if torch:                       # carga real de GPU/CPU (se instalado)
        a = torch.randn(2048, 2048); b = torch.randn(2048, 2048)
        _ = a @ b
    loss = 1.0 / (epoca * random.uniform(0.8, 1.2))
    print(f"[{args.nome}] Época {epoca}/{args.epocas} | loss={loss:.4f}")
    time.sleep(random.uniform(0.5, 1.5))
print(f"[{args.nome}] Treinamento concluído!")

#!/usr/bin/env bash
# teste_fila.sh — 4 jobs simultâneos, 1 GPU
# Ordem esperada: Alta-A, Alta-D, Media-C, Baixa-B
./gpu_queue.sh 1 "Job-Alta-A"  train_job.py --nome Job-Alta-A  --epocas 3 &
./gpu_queue.sh 3 "Job-Baixa-B" train_job.py --nome Job-Baixa-B --epocas 2 &
./gpu_queue.sh 2 "Job-Media-C" train_job.py --nome Job-Media-C --epocas 4 &
./gpu_queue.sh 1 "Job-Alta-D"  train_job.py --nome Job-Alta-D  --epocas 2 &

# Acompanha a fila enquanto há jobs
while [ "$(ls /var/spool/gpu_queue 2>/dev/null | wc -l)" -gt 0 ]; do
    echo "Fila: $(ls /var/spool/gpu_queue | sort | tr '\n' ' ')"
    sleep 2
done
wait
echo "Todos os jobs concluídos!"

5.Monitorar processos na GPU

Enquanto a fila executa, veja quem usa a GPU, quanto de VRAM e qual job espera na fila.

bash 
#!/usr/bin/env bash
# monitor_processos_gpu.sh — monitor em tempo real
# Processos na GPU (NVIDIA)
nvidia-smi --query-compute-apps=pid,process_name,\
used_gpu_memory --format=csv,noheader | \
while IFS=", " read -r pid nome mem; do
    user=$(ps -p "$pid" -o user= 2>/dev/null || echo "N/A")
    echo "  PID=$pid | USER=$user | CMD=$nome | VRAM=${mem}MB"
done

# Utilização por GPU
nvidia-smi --query-gpu=index,name,utilization.gpu,\
memory.used,memory.total --format=csv,noheader,nounits | \
while IFS=", " read -r idx nome util mu mt; do
    echo "  GPU$idx ($nome): util=${util}% | VRAM=${mu}/${mt}MB"
done

# Fila atual
ls /var/spool/gpu_queue 2>/dev/null | sort | nl -w3 -s'. '

6.Isolamento com systemd units

Em produção, o systemd oferece logging via journald, restart automático e controle de recursos por job.

systemd unit 
# /etc/systemd/system/gpu-job@.service
[Unit]
Description=GPU Training Job %i
After=network.target

[Service]
Type=simple
User=ml-user
WorkingDirectory=/data/jobs/%i
ExecStart=/usr/bin/python3 train.py

# Controle de recursos
CPUWeight=50
MemoryMax=16G
IOWeight=50

# Restart automático em falha
Restart=on-failure
RestartSec=10

# Logging centralizado
StandardOutput=journal
StandardError=journal
SyslogIdentifier=gpu-job-%i

[Install]
WantedBy=multi-user.target
bash 
# Iniciar job "experimento-01"
sudo systemctl start gpu-job@experimento-01

# Ver log em tempo real
journalctl -u gpu-job@experimento-01 -f

# Status de todos os jobs
systemctl list-units "gpu-job@*"

# Prioridade com nice/ionice
nice -n 10 python3 train_low_priority.py

Discussão em Grupo

Debate: 1 GPU, muitos usuários

Em grupos de 3–4, debatam com base no cenário do laboratório (1 GPU):

1

A fila é FIFO dentro de cada prioridade. Se um job de alta prioridade demorar 8 h, os de média nunca executam (starvation). Como resolver?

2

flock só funciona no mesmo servidor. Para um cluster com 10 nós GPU, como escalar? Compare com SLURM, Kubernetes e Ray.

3

Um job malicioso pode deletar o arquivo de lock e "roubar" a GPU. Como tornar o sistema mais seguro? (dica: flock + grupos de usuário Linux).

4

systemd com Type=simple não detecta um processo em deadlock sem uso de CPU. Como monitorar e agir automaticamente?
