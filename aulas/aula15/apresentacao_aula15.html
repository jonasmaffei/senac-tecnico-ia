O Problema

1.Race condition em GPUs

Quando vários jobs usam a mesma GPU ao mesmo tempo, competem por memória e capacidade de processamento — com resultados imprevisíveis:

# Sem controle — 4 jobs simultâneos [08:00:00] Job-A inicia — aloca 6 GB VRAM [08:00:01] Job-B inicia — aloca 6 GB VRAM [08:00:02] Job-A: CUDA OOM — apenas 2 GB livres! [08:00:02] Job-B: CUDA OOM — crash silencioso [08:00:03] Job-C: resultados corrompidos (VRAM fragmentada) # Com o lock: [08:00:10] Jobs executam 1 por vez, sem conflito ✅

❌ Sem controle

Jobs competem por VRAM → OOM crash, resultados corrompidos.

✅ Com lock

Exclusão mútua → 1 job por vez, fila automática.

🚀 Com prioridade

Jobs urgentes passam à frente → máxima eficiência da equipe.

Teoria · Exclusão Mútua

2.O lock — 1 job por vez

Um lock é uma marca compartilhada que só um processo pode ter por vez. Enquanto um job o mantém, os outros esperam. É isso que evita dois jobs na GPU ao mesmo tempo.

Como o laboratório faz

lib_gpu15.sh 
# Tenta pegar o lock. Devolve 0 se conseguiu, 1 se ocupado.
# O "lock" é uma PASTA: criar pasta é atômico — se dois
# processos tentam juntos, só um consegue (como o flock -x).
lock_tentar() {
    local dir="$DIR_LOCKS/gpu.lock"
    if mkdir "$dir" 2>/dev/null; then   # deu certo? lock é nosso
        echo "$$" > "$dir/pid"          # gravamos nosso PID
        return 0
    fi
    return 1                            # já existe: alguém está com a GPU
}

# Limpa lock "órfão": se o dono morreu, libera para o próximo.
lock_limpar_obsoleto() {
    local dono=$(cat "$DIR_LOCKS/gpu.lock/pid" 2>/dev/null)
    if kill -0 "$dono" 2>/dev/null; then return 1; fi  # dono vivo: mantém
    rm -rf "$DIR_LOCKS/gpu.lock"                       # dono morto: remove
}

O que o código acima garante

  • Exclusividade: o mkdir atômico garante que só um job cria a pasta — o resto recebe erro e espera.
  • Sem travamento eterno: se um job morre sem liberar, o PID guardado deixa de existir e o lock é removido (kill -0).
  • Portável: no Windows/Git Bash usa a pasta; em Linux/WSL o flock real é preferido (mesmo resultado).

flock -xmkdir atômico
flock -nlock_tentar (não espera)
-w Nparâmetro timeout de lock_adquirir
-u / traptrap finalizar EXIT

Demo · Fila com Prioridade

3.Fila com prioridade (fila_gpu.sh)

A fila é uma pasta de tickets. O nome do ticket começa pela prioridade, então o sort já entrega a ordem certa: 1_… antes de 2_… antes de 3_….

bash · fila_gpu.sh 
# Uso: ./fila_gpu.sh <prioridade> <nome_job> <comando...>
PRIORIDADE="${1:-2}"     # 1=alta  2=média  3=baixa
NOME_JOB="${2:-job_$$}"
shift 2 2>/dev/null || true
COMANDO="$*"
preparar_dirs

# 1) Ticket = prioridade + timestamp + nome.
#    O sort ordena alfabeticamente -> menor prioridade primeiro.
TICKET="${PRIORIDADE}_$(date +%Y%m%d_%H%M%S_%N)_${NOME_JOB}"
echo "$COMANDO" > "$DIR_FILA/$TICKET"          # entra na fila
log "Job '$NOME_JOB' (prio=$PRIORIDADE) enfileirado: $TICKET"

# 2) Espera até o MEU ticket ser o primeiro da lista.
while true; do
    PROXIMO=$(ls "$DIR_FILA" 2>/dev/null | sort | head -1)
    [ "$PROXIMO" = "$TICKET" ] && break          # é a minha vez!
    log "Aguardando: '$PROXIMO' está à frente de '$NOME_JOB'"
    sleep 2
done

# 3) Chegou a vez: pega o lock da GPU e roda o comando.
lock_adquirir "gpu"
bash -c "$COMANDO"

# 4) Sai da fila e libera a GPU.
rm -f "$DIR_FILA/$TICKET"
lock_liberar "gpu"

A ordem sai “de graça”

# tickets na pasta reports/fila/ 1_20260922_003041_715_Job-Alta-A 1_20260922_003042_055_Job-Alta-D 2_20260922_003041_903_Job-Media-C 3_20260922_003041_807_Job-Baixa-B

sort lê o nome de cima para baixo e a ordem é exatamente a de execução: Alta-A → Alta-D → Media-C → Baixa-B.

  • Prioridade = primeiro campo do nome.
  • Timestamp (%N em nanossegundos) desempata e garante unicidade → FIFO dentro da mesma prioridade.
  • Um job por vez garantido pelo lock_adquirir.
Prática · Jobs Python

4.Lançar 4 jobs e ver a fila ordenar

O job que vai rodar

python · train_job.py 
# train_job.py — job de "treino" simulado (não precisa de GPU)
import argparse, time, random, os
try:
    import torch                 # usado só se estiver instalado
except Exception:
    torch = None

parser = argparse.ArgumentParser()
parser.add_argument("--nome", default="Job")
parser.add_argument("--epocas", type=int, default=3)
args = parser.parse_args()

print(f"[{args.nome}] PID={os.getpid()} | Épocas={args.epocas}")

for epoca in range(1, args.epocas + 1):
    if torch:                    # se houver torch, gera carga real
        a = torch.randn(1024, 1024); b = torch.randn(1024, 1024)
        _ = a @ b
    loss = 1.0 / (epoca * random.uniform(0.8, 1.2))
    print(f"[{args.nome}] Época {epoca}/{args.epocas} | loss={loss:.4f}")
    time.sleep(random.uniform(0.5, 1.5))

print(f"[{args.nome}] Treinamento concluído!")

5.Monitorar quem está na GPU

Enquanto a fila roda, o monitor mostra quem usa a GPU, o resumo da placa, quem espera na fila e o dono do lock.

bash · monitor_gpu_proc.sh 
# Uma "volta" do monitor:
uma_volta() {
    echo "── Processos usando a GPU ──"
    # listar_processos_gpu devolve: pid|user|nome|vram|util
    while IFS='|' read -r pid user nome vram util; do
        printf '  PID=%-8s USER=%-10s CMD=%-22s VRAM=%s MB  UTIL=%s%%\n' \
               "$pid" "$user" "$nome" "$vram" "$util"
    done < <(listar_processos_gpu)

    echo "── Resumo da GPU ──"
    while IFS='|' read -r idx util mem tot; do
        echo "  GPU$idx: util=${util}% | VRAM=${mem}/${tot} MB"
    done < <(resumo_gpu)

    echo "── Fila (ordem de execução) ──"
    ls "$DIR_FILA" | sort | nl -w3 -s'. '

    echo "── Lock da GPU ──"
    cat "$DIR_LOCKS/gpu.lock/pid" 2>/dev/null || echo "  Livre"
}

Saída de exemplo (GPU AMD real)

── Processos usando a GPU ── PID=19656 USER=Jonas CMD=python VRAM=N/A MB UTIL=2% ── Resumo da GPU ── GPU0: util=2% | VRAM=2409/12272 MB (19%) ── Fila (ordem de execução) ── 1. 1_..._Job-Alta-A 2. 1_..._Job-Alta-D 3. 2_..._Job-Media-C ── Lock da GPU ── 1960

🪟 Windows vs. Linux

No Windows, listar_processos_gpu usa os contadores de desempenho (AMD) via PowerShell inline; em Linux usa nvidia-smi. O resto do monitor é idêntico.

🔎 Diagnóstico no Linux: nvidia-smi pmon (processos ao vivo), htop, ps aux | grep python, lsof reports/locks/* (quem tem o lock) e strace -p PID.

6.Isolamento com systemd units

Em produção, o systemd oferece logging via journald, restart automático e controle de recursos por job.

systemd unit 
# /etc/systemd/system/gpu-job@.service
[Unit]
Description=GPU Training Job %i
After=network.target

[Service]
Type=simple
User=ml-user
WorkingDirectory=/data/jobs/%i
ExecStart=/usr/bin/python3 train.py

# Controle de recursos
CPUWeight=50
MemoryMax=16G
IOWeight=50

# Restart automático em falha
Restart=on-failure
RestartSec=10

# Logging centralizado
StandardOutput=journal
StandardError=journal
SyslogIdentifier=gpu-job-%i

[Install]
WantedBy=multi-user.target
bash · operar o serviço 
# O "%i" do unit vira o nome depois do @.
# Iniciar o job:
sudo systemctl start gpu-job@experimento-01

# Acompanhar o log em tempo real (journald):
journalctl -u gpu-job@experimento-01 -f

# Ver todos os jobs que existem:
systemctl list-units "gpu-job@*"
bash · prioridade de processo 
# nice: prioridade de CPU (19 = mais baixa)
nice -n 19 python3 train.py

# ionice: prioridade de disco (classe 3 = "idle")
ionice -c 3 python3 train.py

# renice: muda a prioridade de um job JÁ rodando
renice -n -5 -p 12345

Discussão em Grupo

Debate: 1 GPU, muitos usuários

Em grupos de 3–4, debatam com base no cenário do laboratório (1 GPU):

1

A fila é FIFO dentro de cada prioridade. Se um job de alta prioridade demorar 8 h, os de média nunca executam (starvation). Como resolver?

2

flock só funciona no mesmo servidor. Para um cluster com 10 nós GPU, como escalar? Compare com SLURM, Kubernetes e Ray.

3

Um job malicioso pode deletar o arquivo de lock e "roubar" a GPU. Como tornar o sistema mais seguro? (dica: flock + grupos de usuário Linux).

4

systemd com Type=simple não detecta um processo em deadlock sem uso de CPU. Como monitorar e agir automaticamente?
