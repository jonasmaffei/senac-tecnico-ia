Agentes de Código: Harness, RAG, Skills e Vibe Coding

Como as ferramentas “agent-first” (Antigravity CLI, opencode, Claude Code) funcionam por dentro — e como usá-las com critério no dia a dia do desenvolvimento.

Contexto

1.A era “agent-first”

Ferramentas de linha de comando com agentes de IA mudaram o jeito de programar. Elas rodam no terminal onde o desenvolvedor já trabalha.

🅰️ Antigravity

Google. CLI agy, IDE e SDK — todos sobre o mesmo harness.

🟢 opencode

Agente de código open source no terminal; mesmo padrão de interação.

🟠 Claude Code

Anthropic. Agente no terminal com foco em edição de código.

🧩 Todos compartilham a mesma ideia: um agente que lê o projeto, planeja, usa ferramentas (ler/escrever arquivos, rodar comandos) e verifica o resultado.
Teoria · Harness

2.O que é um harness?

O harness é a “armação” que transforma um modelo de linguagem em um agente que age no mundo: ele gerencia o loop, as ferramentas, o contexto e as permissões.

🧠 Modelo (LLM)raciocina e decide o próximo passo
🔁 Loop agênticopensar → agir → observar → repetir
🧰 Ferramentas (tools)ler/escrever arquivos, rodar comandos, buscar na web
📦 Contextoo que o agente “vê” a cada passo
🔒 Permissõeso que ele pode fazer sem pedir aprovação
🔧 Analogia: o modelo é o motor; o harness é o chassi com volante, freio e air-bag. Sem harness, o modelo “fala”; com harness, ele dirige.
🍎 Caso real: Google chama de “shared agent harness” o núcleo que a CLI e a IDE da Antigravity compartilham — mesma capacidade, superfícies diferentes.
Teoria · Agente

3.O agente e o loop agêntico

Um agente não responde uma pergunta: ele persegue um objetivo em vários passos, decidindo quando usar cada ferramenta.

👁️Observarler o projeto e o pedido
→
🗺️Planejarlistar arquivos e passos
→
⚙️Agireditar, rodar, testar
→
✅Verificarrodar testes e corrigir

🧰 Ferramentas típicas

Ler/editar arquivos, executar comandos no terminal, buscar no código, consultar a web, e — nas CLI modernas — subagentes em paralelo.

📏 Limite de contexto

A “janela” do agente é finita. Contexto demais vira ruído; de menos, ele chuta. Por isso existem skills e RAG.

Teoria · Skills

4.Skills: conhecimento empacotado

Uma skill é uma pasta com instruções que ensina o agente a fazer uma tarefa do seu jeito — um padrão reutilizável.

Como funciona

  • Descoberta: o agente vê a lista de skills disponíveis
  • Ativação: se for relevante, ele lê as instruções completas
  • Execução: segue o passo a passo da skill
📄 Cada skill vive em .agents/skills/<nome>/SKILL.md (convenção aberta, usada pela Antigravity).

Estrutura de uma skill

my-skill/ ├── SKILL.md # instruções + descrição ├── scripts/ # opcional ├── examples/ # opcional └── resources/ # opcional
💡 Boas skills fazem uma coisa bem e têm descrição clara — é a descrição que o agente lê para decidir usá-la.
Teoria · RAG

5.RAG: dar conhecimento ao agente

RAG (Retrieval-Augmented Generation) = buscar a informação certa e injetar no contexto antes de o modelo responder. Em vez de “decorar tudo”, o agente consulta na hora.

❓Pergunta
→
🔎Buscarno código, docs, base
→
📄Trechos relevantes
→
💬Respostacom base no que achou

✅ Por que ajuda

Reduz “invenção” (alucinação), usa dados atualizados e cita a fonte (o trecho recuperado).

⚠️ Cuidado

Se a busca traz o trecho errado, a resposta sai errada. Recuperar bem é metade do trabalho.

🔗 No agente de código, “RAG” muitas vezes é a busca no próprio repositório — por isso ele “sabe” onde as coisas estão no seu projeto.
Prática crítica · Vibe Coding

6.Vibe coding: o que é e onde escorrega

Vibe coding é deixar o agente gerar o código a partir de instruções em linguagem natural, iterando pelo “feeling”. É rápido para prototipar — e perigoso sem verificação.

👍 Quando brilha

  • Protótipos e provas de conceito
  • Tarefas repetitivas e “cola”
  • Explorar uma ideia rapidamente

👎 Onde escorrega

  • Código que “parece” certo mas falha nas bordas
  • Faltam testes e revisão humana
  • Segurança, dados sensíveis e segredos
🧭 Regra de ouro: sem verificação (testes, build, leitura do diff), vibe coding vira dívida técnica. O agente acelera; você responde pelo resultado.
Prática · Ferramenta

7.Antigravity CLI (agy)

A CLI da Google é a superfície no terminal para trabalhar com agentes. Leve, rápida e feita para quem vive no shell.

Começando

# instala o cliente (Windows/PowerShell) irm https://antigravity.google/cli/install.ps1 | iex # entra na pasta do projeto e abre a TUI agy
📄 Ao abrir, o agente indexa o projeto e propõe um plano antes de editar.

Recursos que vamos ver

  • Subagentes: tarefas em paralelo (/agents)
  • Slash commands: /skills, /diff, /rewind
  • Permissões: revisar antes de escrever/rodar
  • Verificação: /diff para revisar cada mudança
Prática · Boas práticas

8.Como trabalhar bem com um agente

  • Explore → Planeje → Execute: peça o plano antes do código
  • Loop de verificação: tenha testes e mande o agente rodá-los
  • Contexto enxuto: aponte os arquivos certos (@arquivo)
  • Regras do projeto: um AGENTS.md na raiz
  • Interrompa cedo: esc quando ele se perder
  • Volte atrás: /rewind para um ponto estável

📄 Regras do projeto

Um arquivo AGENTS.md (ou equivalente) na raiz descreve padrões, comandos de teste e avisos — o agente lê isso antes de sugerir mudanças.

🔒 Permissões

Comece no modo mais cauteloso (revisar antes de executar) e só depois afrouxe — nunca dê “sempre pode tudo” no primeiro contato.

1

Onde o harness termina e a responsabilidade do engenheiro começa? Quem responde por um bug gerado pelo agente?

2

Em que situações o RAG resolve mais que “decorar” os dados no modelo? Dê um exemplo do seu setor.

3

Uma skill bem escrita é como um manual: o que ela deveria conter para o agente acertar de primeira?

4

Vibe coding sem testes é aceitável num projeto real? Como você convenceria um colega a mudar de prática?
