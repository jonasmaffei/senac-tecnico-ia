Teoria · CPU

1.O que é um processo?

📦 Processo

  • Unidade independente de execução
  • Espaço de memória próprio e isolado
  • Comunicação via IPC (pipes, sockets, shared memory)
  • Criação mais custosa (fork do SO)
  • Contorna o GIL do Python → ideal para CPU-bound
  • Ex.: cada worker do DataLoader do PyTorch

🧵 Thread

  • "Processo leve" dentro de um processo
  • Compartilha memória com outras threads
  • Comunicação simples e rápida
  • Criação mais barata
  • O GIL limita paralelismo CPU-bound
  • Ótima para I/O-bound (downloads, disco)
💡 Isolamento é a chave: se um processo falha, os outros continuam. Se uma thread falha, pode derrubar o processo inteiro.

🔒 O que é o GIL?

O Global Interpreter Lock é um mutex que permite apenas uma thread Python executar bytecode por vez — mesmo em CPUs multi-core.

Por isso, threading não acelera tarefas CPU-bound. Use multiprocessing para essas. Bibliotecas como NumPy e PyTorch liberam o GIL durante operações nativas (por isso escalam bem).

Teoria · Threads na GPU

3.Warps, blocos e grades

Na GPU, o modelo é radicalmente diferente: dezenas de milhares de threads simultâneas, seguindo uma hierarquia rígida.

Thread
menor unidade · 1 dado · registradores próprios
Warp (NVIDIA) / Wavefront (AMD)
32 threads · mesma instrução (SIMD) · unidade de escalonamento
Bloco (Block)
grupo de warps · shared memory · 1 SM · até 1024 threads
Grade (Grid)
todos os blocos · o problema completo
🧭 Regra de ouro: mapeie 1 thread = 1 dado (1 pixel, 1 elemento). O hardware distribui os blocos pelos SMs automaticamente.
Teoria · Alerta de performance

4.Divergência de warp

Se threads do mesmo warp tomam caminhos diferentes num if/else, a GPU executa ambos os caminhos serialmente, desativando as threads que não correspondem.

⚠️ Isso reduz drasticamente a performance. Evite condicionais dentro de kernels sempre que possível — ou organize os dados para que todo o warp siga o mesmo caminho.
# warp com 32 threads if (threadIdx.x % 2 == 0) { // 16 threads executam aqui } else { // depois, as outras 16 aqui } # resultado: as duas metades rodam em série
  • Warp = 32 threads sempre em lockstep (SIMD).
  • Divergência = perda de ciclos com threads ociosas.
Demonstração · Na prática

5.Threading vs. multiprocessing

A mesma tarefa CPU-bound (contar primos), feita de três formas. O resultado expõe o GIL.

conceito 
# processo isolado (contorna o GIL)
Pool(processes=4).starmap(f, args)

# threads (o GIL segura CPU-bound)
[t.start() for t in threads]
[t.join()  for t in threads]

Resultado esperado

Demonstração · O outro lado do GIL

6.Quando threading ajuda: I/O

Em tarefas I/O-bound (rede, disco), o Python libera o GIL enquanto espera. Aí as threads esperam em paralelo — ganho real.

conceito 
# durante o I/O o GIL é liberado
threads = [Thread(target=baixar, args=(u,))
           for u in urls]

Resultado esperado

EstratégiaTempo
Sequencial (I/O)~3.0s
Threading (I/O)~0.5s
📄 Rode scripts/io_bound.py.
📌 Regra geral: CPU-bound → multiprocessing; I/O-bound → threading (ou asyncio).

7.Configurando blocos e threads

Variando threads_por_bloco (32 a 1024) e medindo o tempo, descobrimos o ponto ótimo.

conceito 
blocos = (N + threads - 1) // threads
soma[blocos, threads](a_d, b_d, c_d)

256 threads/bloco costuma ser o ótimo: é múltiplo de 32 (1 warp) e maximiza a ocupação do SM sem estourar o limite do bloco.

8.htop e nvtop

📊 htop (CPU)

  • Uso de cada núcleo em tempo real
  • Processos e threads (tecle H)
  • RAM e swap

🎮 nvtop (GPU)

  • Uso da GPU e da VRAM
  • Temperatura e energia
  • Processos na GPU (NVIDIA e AMD)
🔎 Experimento: rode o benchmark e observe no htop o multiprocessing acender vários núcleos, enquanto o threading mantém praticamente um ocupado (GIL). No Windows, use scripts/monitor_processos.py.
