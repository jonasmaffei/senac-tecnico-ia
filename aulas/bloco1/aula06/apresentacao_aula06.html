Teoria · Estrutura de diretórios

2.Onde as GPUs aparecem no Linux

CaminhoO que contém
/dev/nvidia*Arquivos de dispositivo das GPUs NVIDIA (nvidia0, nvidiactl)
/proc/driver/nvidia/Info do driver em tempo real: versão, GPUs, clients
/sys/class/drm/Interface sysfs para GPUs via DRM (vendor, classe)
/usr/lib/...Bibliotecas do sistema (libcuda.so, libnvidia*.so)
/etc/modprobe.d/Configuração de módulos do kernel (blacklist, opções)
/var/log/Logs: syslog, kern.log, nvidia-installer.log
💡 Pseudo-arquivos: /proc e /sys não ocupam disco — são uma janela viva para o kernel. Ferramentas como htop e nvtop leem exatamente daí.
Teoria · Explorando

3.Lendo o hardware como arquivos

No Linux, até o estado do processador e da GPU pode ser lido como texto. Um único comando revela o modelo da CPU; outro, a saúde da GPU:

🧠 CPU e memória

cat /proc/cpuinfo mostra o processador; cat /proc/meminfo, a RAM. São arquivos que “não existem no disco” — o kernel os gera na hora.

🎮 GPU

As placas aparecem em /dev (dispositivos), /sys (estado) e /proc/driver (driver). É daí que htop e nvtop leem.

🇧🇷 Caso real: as distribuições Linux expõem quase tudo em /proc e /sys — por isso um servidor de IA se monitora com poucos comandos, sem instalar nada.
📄 No laboratório, rode laboratorio_windows/1_inspecionar.sh (comentado linha a linha).
Demo · Verificar drivers

4.Drivers: a causa nº 1 de falhas

✅ Driver funcionando

A placa responde e informa nome, VRAM e temperatura.

$ nvidia-smi -L GPU 0: Tesla T4 (UUID: GPU-...) $ rocm-smi --showmeminfo vram VRAM Total: 24560 MB

❌ Driver ausente

O utilitário existe, mas não consegue falar com a placa — o erro mais comum ao chegar num servidor novo.

NVIDIA-SMI has failed because it couldn't communicate with the NVIDIA driver.
🔎 Para descobrir qual placa está instalada, use lspci | grep -i vga (funciona para NVIDIA, AMD e Intel). 📄 Implementado em laboratorio_windows/1_inspecionar.sh.
Atividade · Script de status

5.Um script que lista e alerta

O script descobre as GPUs, mostra temperatura/uso/memória e dispara um alerta quando a temperatura passa do limite.

  • Entrada: saída do nvidia-smi/rocm-smi
  • Regra: temperatura > limite → alerta
  • Saída: painel legível + código de erro

🛠️ Suporta NVIDIA e AMD

  • nvidia-smi → NVIDIA
  • rocm-smi → AMD (ROCm)
  • lspci → qualquer placa

O limite é ajustável: LIMITE_TEMP=75.

📄 Rode laboratorio_windows/2_status_gpu.sh (comentado linha a linha).
Teoria · Processos e jobs

6.Manter o treino vivo após o logout

Um job de treino leva horas. Se o SSH cair, o processo morre junto — a menos que ele rode numa sessão persistente.

🖥️ Para ver o que está rodando: htop (CPU) e nvidia-smi pmon (GPU).

Sessões persistentes

FerramentaUso
screensessões após logout (clássico)
tmuxmais moderno, split-screen
nohupsimples, sem interatividade
🔌 Se o SSH caiu no meio do treino, use tmux/screen na próxima vez — a sessão sobrevive à desconexão.
Demo · Automação

7.cron — tarefas periódicas

Roda um comando em horários definidos e encerra. Cada campo é uma posição no tempo:

conceito 
* * * * *  comando
│ │ │ │ └ dia da semana
│ │ │ └── mês
│ │ └──── dia
│ └────── hora
└──────── minuto

Caso real: monitorar a GPU a cada 5 minutos durante todo o treinamento.

# a cada 5 minutos, grava no log */5 * * * * gpu_status.sh >> gpu.log
📄 Mais exemplos em laboratorio_windows/3_agendar.sh.
Demo · Automação

8.systemd — serviços contínuos

Enquanto o cron dispara e encerra, o systemd mantém um serviço sempre ativo — e reinicia sozinho se ele cair.

🔁 Ideal para um monitor de GPU que precisa rodar 24h/7d e sobreviver a falhas e reinícios do servidor.
