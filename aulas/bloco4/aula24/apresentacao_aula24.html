Teoria · Diagnóstico

1.Mapear conexões GPU ↔ PI

Antes de integrar, identifique no repositório do PI os pontos de alto custo computacional que a GPU acelera.

🔁 Loops sobre dados

for sobre imagens/arquivos/batches sem GPU → candidatos a DataLoader CUDA.

🧠 Modelos ML existentes

scikit-learn, Keras ou PyTorch em CPU → migrar para .to('cuda') ou .half().

🔢 NumPy pesado

np.dot, matmul, fft em CPU → reescrever com tensores na GPU.

Prática · Rastreamento

3.W&B e monitor no treino do PI

Reutilize o padrão das aulas anteriores: W&B para métricas de treino e o monitor de GPU para a saúde do hardware.

O que registrar

  • W&B: train/val loss, accuracy, época, config
  • GPU: temperatura, VRAM, utilização, potência
  • Tags: "PI", "GPU", domínio

🔗 Cruzamento

Junte as duas fontes por janela temporal: a GPU estava mais ocupada quando o val/loss caía mais rápido?

Discussão em Grupo

6.Mapa de conexões (2 min por time)

1

Qual componente do PI mais se beneficia de GPU: treino de um modelo, inferência em produção ou pré-processamento? Qual o ganho estimado?

2

O repositório do PI já tem código numpy/sklearn/torch em CPU que poderia migrar para GPU? O que muda — só .to('cuda') ou a estrutura dos dados?

3

Como o monitor de GPU pode ajudar especificamente o PI? Que thresholds fazem sentido para a carga do projeto?

4

Se o PI fosse a produção com RTX 4090, quais 3 ajustes de arquitetura maximizariam o uso da GPU?
